# R3 走查报告

- 日期：2026-10-30
- 范围：失败路径（网关 500 / 超时）、25 段长文、400px 窄屏
- 方式：Node 起服务 → 浏览器真实操作 → 截图（`scripts/r3-walkthrough.mjs`）
- 证据：`docs/evidence/R3/shots/r3-01..r3-08.png`

## 观察

1. 正常翻译 2 段成功，无异常。
2. **网关 500 时**，第 3 段的错误提示是：
   `上游服务返回错误：免费线路暂时不可用，可稍后重试`，带"重试本段"按钮。
3. **网关超时时**，错误提示是：`上游服务返回错误：免费翻译线路不可达`。
4. 粘贴 25 段后，左侧输入框数 26，但表头写"25 段"。多出来的那个是上一步清空留下的空段。
5. 25 段全译耗时 233ms，25 段全部成功。
6. 滚动到中间，段号连续，悬停第 13 行左右同时高亮（R0-08 生效）。
7. 400px 窄屏下顶栏控件不溢出，但控件被折成两行，高度占了小半屏。

## R3-01 为什么是 P1

两件事叠在一起：

**一、内部词汇漏到界面上。** 本站有两条线路（付费模型 / 免费 MyMemory），
这是**架构概念**，读者不该知道。他看到"免费翻译线路不可达"，第一反应是
"我是不是该付钱"，而不是"稍后再试"。

**二、错误只描述了最后一跳。** 实际发生的是：付费线路返回 500 → 降级到免费线路 →
免费线路也失败（假网关的故障开关对两条线路同时生效）→ 最终把**免费线路**的错误抛给用户。
用户看不到"模型线路也挂了"，只看到一个他无法理解的线路名。

正确做法是：所有供应商都失败时，对外只给一条用户能行动的话
（"翻译服务暂时不可用，稍后重试"），每条线路的具体原因进日志。
`errs.Upstream` 的 `hint` 目前直接拼进用户可见文案，需要区分
"给用户看的 message" 和 "给运维看的 detail"。

## R3-02 的成因

不是产品缺陷，是我清空输入框的方式造成的：把每个 textarea 的 value 置空并 dispatch input，
空段会保留（`updateSource` 只在粘贴路径丢弃空段）。随后粘贴整篇，`setDocument` 替换内容，
但那个空段留了下来。

暴露的真实问题是：**表头 `stats.total` 不计空段，而 DOM 里空段仍然占一个框**，
两个数字对不上。用户全选删除后，会看到一个"·"编号的空框 + 表头"0 段"。

## R3-03 的成因

`TopBar` 的 `.topbar__row--controls` 是 `flex-wrap: wrap`，
窄屏下语言对、风格、模型、术语、动作按钮依次换行，占掉约 200px 高度。
手机上第一屏只能看到顶栏和一行原文。

## 本轮修了什么

**R3-01 已修**（走查当天修完，没留到 R4）。

改法不是换文案，是把"给用户看的话"和"给运维看的细节"拆开：

- `internal/httpapi/translate.go` 的 `userMessage()` 增加按错误码分流：
  `UPSTREAM_FAILED` / `UPSTREAM_TIMEOUT` 一律只返回
  **"翻译服务暂时不可用，请稍后重试"**，不再拼接 provider 的 hint。
  线路名、挂在哪一跳，全部留给日志。
- 降级时不再往段落错误里拼"本站额度已用完，已切到免费线路；"——
  页面顶部本来就有降级横幅，段落里再重复一遍是把同一句运维话术说两次。
- 失败日志改成**一次请求一条**（`slog.Warn("翻译失败", "failed", n, "err", firstErr)`），
  不在循环里逐段打：20 段全挂会刷 20 行，把日志淹没。
- 三个门禁的白名单同步加了 `翻译失败`，并注明"用例 2b 故意让一段超长失败"。

修复后重跑：

```
网关 500 后，错误提示="翻译服务暂时不可用，请稍后重试"，重试按钮可见=true
网关 timeout 后，错误提示="翻译服务暂时不可用，请稍后重试"
```

R3-02、R3-03 留到 R4：都是 P2，且 R3-02 需要先想清"空段到底该不该占一个框"，
不是改个数字的事。
